# Controlled task execution facts

G3 introduces an operator-controlled task lifecycle for active baselines whose workforce/equipment/licenses are supported. These API commands authorize a task start and record an operator's completion observation. They do not issue physical machine commands or establish that an outside provider performed work. External effects, inbox/source authentication and ambiguity reconciliation require their owning G4/integration contracts.

Activation creates Planned task state from the exact immutable schedule. A start requires current project Execute permission, Active baseline state, unchanged definition, the current task version, a server time inside its half-open reserved interval and completed dependencies. PostgreSQL locks named license pools and checks exact plan/project/task/interval/seat ownership. The SQL guard observes sorted locked catalog/calendar ownership and current resource revisions. Parent/activation locks serialize task commands against cancellation and other task commands. This is an owning-store observation with trusted worker/administrator assumptions, not a cross-store atomic snapshot or hardware safety interlock.

Each task has Planned, Running and Completed state; actual start and completion times are separate from planned intervals. Start uses the database clock. Completion supplies a microsecond effective time between actual start and the database recording time. Late completion remains a true immutable fact with `OutsideReservation`; it is not erased or labeled on-time. Unfinished dependencies block downstream starts. Further resource availability, disruption and changes need G5 adaptive operations rather than silent movement of intervals.

Stable command IDs are scoped to plan/task and bound to actor, mutation, expected task version and supplied effective time. The original accepted or rejected decision is append-only and shares a commit with task state and a typed event. Original replay returns its retained fact even after later progress; changed data/actor under that identity conflicts. A rejected start keeps the task Planned and records no actual start. A changed condition requires a fresh command identity; it cannot rewrite an earlier rejection. Task versions and activation/review versions are distinct.

Once any task starts, generic reservation cancellation is rejected and ordinary definition edits are blocked while that execution remains live. Started/completed work must use future explicit forward recovery/adaptive revision. When every task is reported complete, the coordinator releases original license/resource ownership and reaches `Completed`. This means reported baseline work and ownership release; it does not close accounting, certify customer acceptance or implement project financial closure.

Task state and facts have tenant row security and composite ownership foreign keys. Facts allow SELECT/INSERT only to runtime roles and have an ORM mutation guard. The database-owner threat boundary remains unchanged. Read APIs expose both current progress and ordered original facts so callers can distinguish planned work, accepted commands, rejected attempts and overruns.

Routes: `/api/v1/projects/{projectId}/execution-plans/{id}/tasks`. GET lists task state/version and facts. POST `/{taskId}/start` takes `{ commandId }`; POST `/{taskId}/complete` takes `{ commandId, effectiveAt }`. Writes require a quoted task-version `If-Match`, production `ManageResources` and project Execute permission. Accepted original facts return 200; durable rejected decisions 422; missing ETag 428; stale task version 412; identity conflict 409; foreign/unavailable scope 404. Responses are no-store. A fact's `TaskVersion` is its original recorded version; reads return the current version.

The real-store lifecycle test uses actual planned one-minute intervals and the database clock: it races first starts, preserves original retry, refuses generic cancellation/definition replacement after start, reaches the second interval with an incomplete predecessor, retains an overrun completion, starts the dependent task, reports completion and releases ownership. Other tests remove actual allocation/seat ownership, check original negative decisions, signed HTTP/project authority, restricted PostgreSQL policies and immutable history. `examples/execution-task-demo.ps1` performs the Development HTTP/worker path with real time.
